# GPU-Aware AI Inference Platform

A backend infrastructure demonstration aligned with AI Cloud and model-serving engineering roles. It implements a bounded Redis work queue, asynchronous inference jobs, worker execution, basic observability, containerization, and a Kubernetes Helm chart with optional GPU scheduling.

**Project status:** Runnable local implementation with a deterministic mock backend. Real Hugging Face inference and NVIDIA GPU scheduling are optional deployment modes that require additional dependencies and hardware. No production-scale or multi-GPU performance claims are made.

## Architecture

```text
Client -> FastAPI -> Redis queue -> Worker -> Model backend
             |            |             |
             |            +---- Job status/result
             +-- /metrics -> Prometheus -> Grafana
```

## Run locally (Mac CPU-compatible)

```bash
docker compose up --build -d
curl -s http://localhost:8000/health/ready
curl -s -X POST http://localhost:8000/v1/infer -H 'Content-Type: application/json' -d '{"prompt":"Explain GPU batching","max_new_tokens":24}'
curl -s http://localhost:8000/v1/jobs/REPLACE_WITH_JOB_ID
```

Other local endpoints: API docs at http://localhost:8000/docs, Prometheus at http://localhost:9090, Grafana at http://localhost:3000 (admin / localdev, for local use only).

The mock backend is intentionally deterministic and does not call an LLM. To run real CPU/GPU model inference, build `Dockerfile.model`, configure `MODEL_BACKEND=transformers`, and select `MODEL_ID`. Model weights download at first use; allow network access and adequate memory. On Kubernetes, GPU usage requires NVIDIA GPU nodes, working drivers and device plugin; merely setting a GPU resource limit does not install those prerequisites.

## Test and benchmark

```bash
python -m pip install -e '.[dev]'
pytest -q
ruff check app tests scripts
python scripts/load_test.py --requests 100 --concurrency 10
```

Benchmark output measures completed jobs, throughput, mean and p95 end-to-end latency. Mock-mode numbers reflect queue mechanics and overhead, **not GPU throughput**. Capture hardware, backend, model, concurrency, and configuration alongside every reported measurement.

## Kubernetes with Helm

```bash
helm lint deploy/helm/gpu-inference
helm upgrade --install gpu-inference deploy/helm/gpu-inference -n ai-inference --create-namespace
kubectl -n ai-inference port-forward svc/gpu-inference-api 8000:8000
```

The image must be built and accessible to the cluster before installation. For example, in a local `kind` cluster, build `gpu-inference:0.1.0`, then run `kind load docker-image gpu-inference:0.1.0`. For remote clusters, push the image to a registry and override `image.repository` and `image.tag`.

An example GPU override is at `deploy/helm/gpu-inference/values-gpu.example.yaml`. Build and publish a model-enabled image from `Dockerfile.model` before using it.

The chart configures CPU-based HPA for **API pods only**, rather than pretending to scale model workers using GPU usage. A GPU-aware worker autoscaler (KEDA queue depth metrics, capacity-aware placement, or another scheduler) is a follow-on enhancement. The bundled single Redis pod has no persistence or HA and is for demonstration use, not production.

Terraform example for deploying the Helm chart into an existing Kubernetes cluster:

```bash
cd deploy/terraform
terraform init
terraform plan
terraform apply
```

## API contract

`POST /v1/infer` returns HTTP 202 with `job_id`. `GET /v1/jobs/{job_id}` returns queued, running, completed, or failed status. The queue returns HTTP 429 when full. Redis outages return HTTP 503. Job results expire after the configured TTL.

## Honest limitations and next milestones

- No authentication, per-user quotas, or secret management; do not expose publicly without adding these protections.
- Queue consumption uses `BLPOP`; a worker crash after dequeue can leave a job in `running` state. A reliable production implementation should use Redis Streams consumer groups or pending-job recovery.
- Model instances are single-worker processes; distributed inference and GPU-aware worker autoscaling are not implemented.
- The default model-serving backend is simulated, so local tests do not demonstrate actual GPU execution.
- The chart's optional `ServiceMonitor` requires the Prometheus Operator CRD and should be enabled only if it is installed.
